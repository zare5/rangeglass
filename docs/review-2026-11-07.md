# Review of the first release

Reviewed on 2026-11-07, against v0.1.0 (`930a3e6`). The findings below were reproduced with local HTTP servers before changes were made. This review does not certify the absence of other defects.

## Product judgment

Rangeglass has a useful, narrow role: helping developers and service maintainers diagnose broken range/resume behavior through a download endpoint. It saves repeated manual requests and correlates several responses. It is less compelling as an everyday consumer utility; most successful downloads need no preflight.

The [research](research.md) establishes that these failures occur, but does not establish adoption of Rangeglass. Downloads, user reports, and independent usage are needed to validate the product. Good documentation and relevant keywords help discovery; they do not guarantee recommendations, users, or stars.

## Reproduced findings and fixes

| Finding | v0.1.0 behavior | v0.2.0 behavior |
| --- | --- | --- |
| Full response to a mismatching `If-Range` is empty, too short, encoded, or changes length/ETag. | Could report PASS. | Checks sampled body length, identity encoding, total length, ETag, and overlapping bytes. |
| 403/429 interrupts a scan, or the fallback returns 503. | Could call an access problem a protocol failure, or return a warning with exit 0. | Stops subsequent requests and reports INCONCLUSIVE unless a concrete failure was already observed. |
| A bad range is followed by a network error. | The incomplete-scan verdict could conceal the earlier failure. | FAIL takes precedence; both findings remain in the report. |
| A request beyond the known end receives 206. | Warning, exit 0. | Failure; a changed total in a 416 is also detected. |
| A valid response is a contained subset starting after the requested first offset. | Conservatively rejected. | Accepted with a warning; comparison uses the actual offset. |
| Redirect limit is reached. | Report could include a destination that was never followed. | Records only the five followed hops. |
| Suffix syntax receives 501 while explicit tail offsets work. | Treated the rejected suffix as a failed range, without testing explicit tail offsets. | Tries one bounded explicit tail request, retains a warning, and continues conditional checks. |

The RFC basis for partial subsets and conditional requests is [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), particularly sections 13.1.5, 14.2, and 15.3.7. The first release's tests covered typical broken ranges but missed important alternate responses. Green tests alone were insufficient.

Public checks during this review: the Python 3.14.0 source-file URL passed the core checks with 6,145 application body bytes read. On this project's v0.1.0 GitHub release-asset route, suffix syntax returned 501 while explicit tail offsets returned 206; a deliberately mismatching If-Range also returned 206. These are route-specific observations on the review date, not claims about every GitHub download or proof that ordinary downloads are broken. The latter conditional-resume finding must remain a failure even when explicit ranges work.

## Documentation and discoverability

The original README already explained installation, output, limits, and alternatives. The main gaps were identifying the audience quickly and using the phrases people encounter when troubleshooting. The update adds a symptom table, direct-file guidance, curl error 33, HTTP Range support, interrupted downloads, Content-Range, ETag, If-Range, CDN/proxy debugging, and Chinese equivalents in natural examples.

The Markdown exporter supports a concrete workflow: run a diagnostic and attach a readable report to a maintainer's issue. Hostnames and paths remain visible, as documented; URL queries and request-header values are omitted.

## Remaining limits and worthwhile next steps

1. **Validate usefulness with real reports.** Collect reproducible examples from users who are already troubleshooting downloads. This has higher value than adding unrelated features.
2. **Make sensitive direct URLs easier to supply.** An environment/stdin input option would keep signed URLs out of command histories and process arguments.
3. **Add browser CORS diagnostics as a distinct optional mode.** Range requests succeeding in a CLI does not establish that DuckDB-Wasm or browser media clients can read them. This would need Origin/OPTIONS handling and separate verdicts.
4. **Consider HTTP/2 and HTTP/3 only with evidence.** The standard-library HTTP/1.1 implementation keeps installation small; additional protocols introduce runtime dependencies and more test requirements.

Known boundaries remain: sampled bytes are not whole-file integrity, URL expiry cannot be predicted, server behavior can change later, and socket timeouts are not a whole-command deadline. No GUI, download accelerator, or large hosting service is needed to improve the current tool.
